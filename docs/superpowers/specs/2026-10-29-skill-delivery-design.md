# Skills: your own, in every environment

Written 29 October 2026. People need to add their own skills, for themselves, a team, a project or a workspace, and every execution environment should run with a set it can name. This note records what happens today, the design, what was rejected (a gcsfuse mount, an image volume for the document runtime, a per-actor skills cache for now) and the order of work. An adversarial review of the first draft against the code found that its transfer plan saved nothing on the default path and opened isolation holes; this version is rebuilt on that review.

## What happens today

- **Built-in skills** live under `plugins/branchyard/skills/` and are compiled into `by` (`crates/branchyard-provision/src/skills.rs`, generated by `tools/artifact_assets.py`). Before each turn, `capabilities::stage` writes the catalogued skills into `.branchyard/capabilities/` of a private home, or into `<state>/capabilities/<blake3(branch)>` when there is none (`crates/branchyard/src/capabilities.rs:28-95`). It writes only files that changed (`crates/branchyard-provision/src/apply.rs:51-75`); a second staging writes nothing (`capabilities.rs:170`). The harness learns of them from one line prepended to each prompt (`engine.rs:1546`, `capabilities.rs:89-92`), not from its native skill folders. Nothing deletes the per-branch caches. The staged tree carries no version or digest.
- **Substrate**: an actor cannot mount anything (`placement.rs:10-15`). Each turn pushes the worktree and the whole private home, skills included, and pulls the home back (`placement.rs:704-737`, `transfer.rs:1037-1074`). Actors are destroyed after each turn by default (`keep = "destroy"`, [sandbox snapshots](../../sandbox-snapshots.md)), and the kept-actor path is unqualified, so on the default path every turn starts a fresh actor and the skills cost about 319 KB each way.
- **The document runtime** (the hash-locked Python packages, LibreOffice, Poppler, fonts) is in no actor image. `deploy/Dockerfile.agy` (Ubuntu 24.04) carries the harness and `by`; `deploy/Dockerfile.artifacts` (Debian bookworm, `python:3.11-slim`) installs the runtime but is a separate, optional image. `run.py setup` installs packages at run time, which Substrate's default-deny egress refuses (`crates/branchyard-substrate/src/egress.rs:8-10`). Document authoring inside a Substrate actor therefore does not work today.
- **A person's own skills** reach a session only as files in the worktree or as instruction text. User folders such as `~/.claude/skills` disappear under a private home (`lib.rs:1395-1401`). There is no store, namespace, size limit, digest or trust gate for them, and the capability index lists built-in skills only.
- **Native skill folders bypass Branchyard.** Claude Code loads a worktree's `.claude/skills` itself, and a run without a private home also sees `~/.claude/skills` and the other harnesses' user folders. Branchyard's index and gates cover only what Branchyard stages.
- **Startup is barely measured**: one native AGY turn on a GKE gVisor actor settled in about 33 seconds ([console validation](../../console-validation-2026-10-29.md)); no actor-ready, transfer or first-token timing exists.

## Goals

1. Measure startup before changing how anything travels.
2. Anyone can add skills at the scopes they are allowed, and each turn records exactly which skills it ran with.
3. A skill an agent edits during a turn never becomes a trusted skill for its next turn or its children.
4. One person's skills never reach another person's session, fork, snapshot or terminal.
5. No new cloud dependency; air-gapped servers keep working; local and remote resolve the same set.

Not goals: a marketplace, signing infrastructure, or changing what native harnesses load from their own folders.

## The model

A **skill** is a directory with a `SKILL.md` whose frontmatter `name` matches the directory and has a `description`, plus optional `references/` and `scripts/`. Limits: 1 MiB and 200 files per skill; no symlinks, absolute paths or `..`. `check_skill_file` moves from `branchyard-setup` into `branchyard-provision`, which `branchyard` already depends on, and gains a real frontmatter parse.

A skill's **digest** is BLAKE3 over its sorted relative paths and contents. A **skill set** is the list of `(layer, name, digest)` one branch runs with. The set is fixed when the branch is created, and its children inherit it, so a mid-task edit to a stored skill changes new branches only.

**Layers**, most specific first:

| Layer | Who adds it | Where it lives | Status |
|---|---|---|---|
| Repository | Repository writers, through git | `.agents/skills/<name>/SKILL.md`, read from the branch's base commit, never the working tree | v0.3.1 |
| Workspace | Workspace owners | Server store | Next |
| Personal | The person; applies only to sessions they start | Server store | Next |
| Team | Tenant administrators (`admin`) | Server store | Next |
| Built-in | The release | The `by` binary | Today |

Built-in names are reserved; a custom skill appears under its layer, as `repository:style-guide`. Between custom layers the more specific one wins, and the index notes what it shadowed. The index stays within its budgets (4,096 bytes root, 8,192 per detail index); custom skills sit under one generated "Custom" topic, built at run time in Rust from each skill's frontmatter. A set that would exceed the budget is refused when it resolves, naming the largest skills.

`.agents/skills/` is the folder several harnesses already share by convention. A harness that reads it natively will also load it from the working tree on its own; the boundary above applies.

## Trust

- **Repository skills** are text a repository's writers committed, so they get the gate workspace scripts have ([workspace](../../workspace.md)): locally, a person trusts a repository's skill set by digest (`by skills trust`); on a server, they are off unless the operator sets `allow_repository_skills`. A repository's own configuration can never turn them on.
- Because they are read from the base commit, an agent's edits during a turn (committed each turn, `engine.rs:2223`) are not skills until a person merges them and trusts the new digest.
- Server-managed layers (next): a session credential, or any process with `BRANCHYARD_BRANCH` set, may not write skills, the precedent workspace scripts set. Workspace skills are owner-only, since they run with the session owner's connectors and secrets.
- Skills are guidance, not authority: the index labels every custom skill with its layer and who added it. Their scripts run only through the agent's tools, under the session's policy (deny by default) and approvals; reviewer sessions keep their read-only constraint. File modes alone are no defence, since an agent can run `python script.py`; the policy is.

## Recording and measuring (v0.3.1)

- `Provisioned` gains an always-present `skills: {set, entries: [{layer, name, digest}]}`, modelled on its `knowledge` field, so every turn's record names its skills even when nothing changed on disk.
- Each placement records actor-ready time and the bytes and duration of the worktree push, home push and home pull. The first live run after this change produces the numbers that decide whether any transfer change is worth its cost.
- `by rm` deletes the branch's `<state>/capabilities/<hash>` cache.

## The document runtime: in the actor image

The runtime belongs in the actor image itself: a stage of `deploy/Dockerfile.agy` installs `deploy/artifacts-requirements.lock` with hashes and LibreOffice, python3-uno, fonts and Poppler from Ubuntu 24.04's own packages, smoke-tested the way `.github/workflows/artifacts.yml` tests the runtime. A template `image` volume cannot do this job: it mounts read-only at one path, mounts may not nest (`ateapi.proto:995-1003`, `:1136-1148`), and LibreOffice and UNO install into `/usr` against the system Python; changing a volume's image also invalidates snapshots. Built-in skills stay in `by`. The image grows by the size of LibreOffice; its size is recorded when it is built.

## Why not a gcsfuse mount

- Substrate's `Volume` has no CSI or inline source. Its dynamic option, `external_volume_template`, provisions from a StorageClass (`ateapi.proto:1150-1166`); the Cloud Storage FUSE CSI driver offers static and ephemeral inline volumes, not that provisioning model (to confirm against current GKE documentation before this is revisited). So an actor cannot mount a bucket today, whatever the cluster has installed.
- Volumes are per template, not per actor, so per-person or per-workspace skills would need a template each, or one bucket every actor can read, which breaks goal 4.
- Air-gapped servers could not use it, against goal 5.

Where a bucket could fit later: large, read-mostly, single-tenant reference data on an operator-built template, if Substrate gains a suitable volume source; until then, a signed-URL download through an explicit egress allowance. Server-managed skills, when they come, are small and stored in the console store the way source documents are (bounded base64 rows), so servers sharing a database share them with no bucket.

## Rejected for now: a per-actor skills cache

Sending skills once per actor per digest only saves anything for kept actors, which are off by default and unqualified. It would also need a bridge protocol version to exclude paths from the home transfer (`crates/branchyard-bridge/src/client.rs:328-353`, one protocol version per bridge), a root-owned location in every actor image, and a content check inside the actor each turn, since anything the actor's user can write the agent can change. Full-scope snapshots would carry one person's skills into another's fork. It comes back only if the recorded timings show the home transfer matters, and then with the hash check and personal layers kept inside the home.

## Order of work

1. **v0.3.1**: skill and set digests in `branchyard-provision` (with `check_skill_file` moved there); the always-present `skills` record; repository skills from `.agents/skills/` at the base commit, gated locally by `by skills trust` and on servers by `allow_repository_skills`, in a runtime-generated index; placement timings and bytes; per-branch cache cleanup on `by rm`; docs (`provisioning.md`, `knowledge-skills.md`, `surfaces.md`, the delegate skill, `leaf.md`, the MCP instructions) and regenerated schemas and facts. Hermetic tests, including an agent editing a repository skill with no effect on its next turn.
2. **Next**: the runtime stage in the actor image (built and pushed by the release workflow, so it ships with a release, not from this work); the server-managed store (workspace, personal, team) in SQLite and PostgreSQL, its routes, SDK methods, CLI and console section, per-caller resolution, and the write refusals above.
3. **Later, if the timings justify it**: transfer changes for Substrate.

## Decisions

The owner decided on 29 October 2026:

- Personal and team skills are on by default once the server-managed store exists, and team skills need no approval by default; an operator setting can require an administrator to approve each team skill's digest.
- Precedence between custom layers: workspace, then repository (project), then personal, then team.

Still proposed, not yet decided: `.agents/skills/` as the repository folder, and repository skills off on servers unless the operator allows them.
