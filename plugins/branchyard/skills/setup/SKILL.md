# Setting up Branchyard

`by init` holds the whole interview: the questions, what it detected, the
defaults, and a validated plan of files. You are its front-end. Never
write these files by hand, and never invent answers the user did not give.

## Choose the topic

| Topic | Writes |
|---|---|
| `project` | `branchyard.toml` (or the user's `~/.config/branchyard/config.toml`): default harness, model, limits, permissions, isolation, check, secrets by name, a server to use |
| `server` | A server configuration with hashed credentials, 0600 token files, tenants and quotas |
| `rig` | A rig TOML: a lead seat and the seats it delegates to |
| `deploy` | `compose.yaml`, its server configuration and generated secret files |
| `plugin` | These skills, into Claude Code or Codex |

If the request is unclear, run `by init --json` and ask which topic.
Before you start, read that topic's notes: `references/project.md`,
`references/server.md`, `references/rig.md`, or
`references/deploy-and-plugin.md`; and `references/protocol.md` once.

## The loop

1. Run `by init <topic> --json --next`. Show the user the `facts` in one
   short list.
2. Ask the `questions`, all of them in one call of your question tool
   (Claude Code: `AskUserQuestion`; a batch never has more than four). Map
   each question as `references/protocol.md` says: `header`, `prompt`,
   its `choices` as options (label and description; the recommended one
   first), `multiSelect` for `multiselect`. Mention `why` when it helps.
   Without a question tool, ask in chat, one numbered list per batch.
3. Write every answer so far into one JSON object keyed by question `id`
   (start from the response's `answers`, which are normalized), save it to
   a file such as `.branchyard/setup-answers.json`, and run
   `by init <topic> --json --next --answers <file>`.
4. If `errors` is not empty, tell the user why each answer was refused and
   ask that question again. Repeat from step 2 until `"done": true`.
5. Run `by init <topic> --answers <file> --dry-run --json`. Show the user
   each file's `path`, `action` and `diff` (never a secret: those have no
   content), the `validation` verdicts and the `commands`. If `valid` is
   false, explain the messages, and change the answers that caused them.
6. Ask for explicit confirmation. Only then run
   `by init <topic> --answers <file> --apply --json`. If it refuses with
   `would_overwrite`, show those diffs again and add `--force` only if the
   user agrees to replace the files.
7. Run the plan's `commands` that validate (`by config validate`,
   `by serve --config … --check`, `by rig check …`), and fix any failure
   by asking again. Then tell the user the next command to try.

## Rules

- Secrets: ask only *where* a secret is (a variable name such as
  `ANTHROPIC_API_KEY`, or `@path` to a file). Never ask for, repeat, write
  or log a secret's value. If the user pastes one, say it was not used and
  suggest they rotate it.
- Tokens are generated by `by init server|deploy` into 0600 files; never
  print them. Point the user at the file.
- Never invent an answer. Only when the user says to use the defaults,
  add `--defaults`, which fills every unanswered question.
- Keep `by` calls single commands without pipes, so permission rules can
  recognize them.
